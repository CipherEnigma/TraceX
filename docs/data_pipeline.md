# TraceX data pipeline (Member 1)

This document is the contract between the data pipeline and the retrieval (Member 2) and LLM (Member 3) code.
Numbers quoted here come from [reports/data_report.md](../reports/data_report.md), which is regenerated by the pipeline.

## Reproduce in one command

```bash
pip install -r requirements.txt
python -m tracex_data all          # download raw data, preprocess NYC, TKY, Massive-STEPS Tokyo, figures, report
python -m pytest tests -q          # unit tests for every pipeline rule
```

The run takes about 1-2 minutes. Outputs go to `data/processed/<dataset>/` (git-ignored, about 150 MB) and
`reports/`. The run is deterministic: compare your sample fingerprints with the table in the data report.

## Datasets

| Key | Source | Used for |
|---|---|---|
| `nyc` | Foursquare TSMC2014 NYC (Yang et al. 2014) | E1, E2, comparison with published numbers |
| `tky` | Foursquare TSMC2014 TKY | E1, E2 |
| `msteps_tokyo` | Massive-STEPS Tokyo (Hugging Face `CRUISEResearchGroup/Massive-STEPS-Tokyo`) | E3 name test, newer-data check |

**Why Tokyo for Massive-STEPS.** The brief asks us to check per-user history length and name coverage first.
`python scripts/profile_massive_steps_cities.py` profiles five candidate cities
([reports/massive_steps_city_profile.md](../reports/massive_steps_city_profile.md)). Tokyo has the highest
name coverage (97% of check-ins, 94% of POIs with an address) and 95% of users have at least three 24-hour
sessions. It also matches TKY for comparison. Its release covers only 2017-18, which serves as the newer-data check.

## Protocol (fixed for every method)

1. **Cleaning.** Drop rows missing user, venue, category or time; drop invalid or (0,0) coordinates; drop exact
   duplicate check-ins (same user, venue and timestamp).
2. **Local time.** Foursquare: UTC time plus the per-row timezone offset. Massive-STEPS: its timestamps are UTC
   (not stated in its README; verified because raw Tokyo bar check-ins peak at 12:00 = 21:00 JST), converted to `Asia/Tokyo`.
3. **Frequency filter** (LLM4POI / Nishida et al.): drop POIs with < 10 check-ins, then users with < 10
   check-ins. Massive-STEPS is too sparse for this (median POI has 1 training check-in), so it keeps all POIs
   and users with >= 5 check-ins. E3 compares conditions within this one dataset, so this does not bias E3.
4. **Chronological split.** On the global timeline, 80% / 10% / 10% of check-ins by time go to train / val / test.
5. **Sessionisation.** Within each user and split, a new trajectory starts at a gap of **>= 24 hours**.
   Trajectories never cross a split boundary.
6. **Pruning.** Trajectories need >= 2 check-ins. Val/test keep only users and POIs seen in training; the
   24-hour rule is re-applied after removing unseen POIs, because removal can open a gap inside a trajectory.
7. **IDs.** `user_id` and `poi_id` are contiguous integers fitted on the training split only
   (`users.csv` and `pois.csv` map back to raw IDs).
8. **Task.** One instance per val/test trajectory: input = prefix (all but the last check-in) + history;
   target = last check-in.
9. **History (fixed definition for the paper).** The user's **training** trajectories that end before the target
   trajectory starts. Every instance has at least one, as the brief requires.
10. **Revisit vs new (E2).** `target_in_history`, `target_in_prefix`, and `is_revisit = target_in_history or target_in_prefix`.
    "New" means the target POI appears nowhere in the model input.
11. **Samples.** `sample_test_500` is a uniform random sample of the test instances with seed 42.
    `sample_test_debug20` is a 20-instance subset of it, for debugging before a full run. Massive-STEPS Tokyo has
    334 test instances, so its "500" sample is the whole test set.

## Reproducing the published setup

| | Ours | Published (brief / LLM4POI) |
|---|---|---|
| NYC check-ins after the 10/10 filter, without de-duplication | 147,938 | 147,938 |
| TKY check-ins after the 10/10 filter, without de-duplication | 447,570 | 447,570 |
| NYC users / POIs (final) | 1,073 / 5,061 | 1,048 / 4,981 |
| TKY users / POIs (final) | 2,281 / 7,829 | 2,282 / 7,833 |

The filter stage matches the published counts exactly. Our de-duplication then removes 250 (NYC) and 577 (TKY)
exact-duplicate rows. TKY's final counts match within 0.1%. NYC keeps about 2% more users and POIs than published.
The likely cause is a difference in how the reference code prunes trajectories, and we report it as a known deviation.

## Output files (`data/processed/<dataset>/`)

| File | Contents |
|---|---|
| `checkins.csv` | `user_id, poi_id, traj_id, split, local_time, category_id, category, lat, lon` (+ `name, address` for Massive-STEPS) |
| `pois.csv` | one row per POI: `poi_id, venue_raw, category_id, category, lat, lon, train_checkins` (+ `name, address`) |
| `users.csv` | `user_id, user_raw` |
| `trajectories.jsonl` | every trajectory in every split |
| `instances_val.jsonl`, `instances_test.jsonl` | all prediction instances |
| `sample_test_500.jsonl`, `sample_test_debug20.jsonl` | the fixed evaluation samples (+ `_ids.txt`) |
| `stats.json` | statistics, cleaning log, POI coverage, revisit rates, sample fingerprints |
| `leakage_report.json` | result of each leakage / integrity check (the pipeline fails if any check fails) |

### Check-in record (inside trajectories and instances)

```json
{"poi_id": 812, "category": "Coffee Shop", "time": "2012-11-27 08:14:03", "hour": 8, "weekday": 1}
```

`weekday`: Monday = 0. Massive-STEPS records also carry `"name"`.

### Trajectory record

```json
{"traj_id": 15, "user_id": 0, "split": "train", "start_time": "...", "end_time": "...", "checkins": [ ... ]}
```

### Instance record

```json
{
  "instance_id": "nyc-test-1234", "dataset": "nyc", "split": "test",
  "user_id": 42, "traj_id": 1234,
  "history_traj_ids": [1200, 1201, 1215],
  "prefix": [ {check-in}, ... ],
  "target": {check-in},
  "target_in_history": true, "target_in_prefix": false, "is_revisit": true,
  "n_history_trajs": 3, "n_history_checkins": 17
}
```

**Allowed from the target: only its time** (`target["time"]`, `target["hour"]`, `target["weekday"]`). This
follows LLM-Mob and Nishida et al., which give the model the time of the next check-in. Every method must use the
same rule: the frequency heuristic scores by the target hour and weekday, and both LLM prompts show the target time.
**Never use `target["poi_id"]`, `target["category"]`, `target["name"]`, `target_in_history`, `target_in_prefix` or
`is_revisit` in a prompt or a retrieval query.** They exist only for scoring and for the E2 breakdown.

## Using the data from Python

```python
from tracex_data.api import load_dataset

ds = load_dataset("nyc")                       # "nyc", "tky" or "msteps_tokyo"
for inst in ds.instances("sample_test_debug20"):
    history = ds.history(inst)                 # list of trajectory dicts, oldest first
    current = inst["prefix"]                   # the trajectory so far
    gold = inst["target"]["poi_id"]            # for scoring only
pois = ds.pois                                 # DataFrame; names/addresses for msteps_tokyo
```

- **Member 2 (retrieval):** the candidate pool for Jaccard / LCS / TF-IDF / BM25 demonstrations is
  `ds.history(inst)`. Use `ds.train_trajectories()` for corpus statistics such as IDF and POI frequency.
- **Member 3 (LLM):** LLM-Mob "recent" context = the last trajectories of `ds.history(inst)` plus `inst["prefix"]`.
  For E3, take names from the check-in `name` field or `pois.csv`. About 15% of Tokyo POIs share a name with another
  POI (chains), so aliases must be assigned per `poi_id`, not per name.

## Leakage checks (all must pass)

The checks cover temporal order of splits, one split and one user per trajectory, no gap >= 24 h inside a
trajectory, val/test users and POIs present in train, the POI index fitted on train only, the target equal to the
last check-in and absent from the prefix, history only from train and strictly before the target trajectory, every
instance having history, unique instance IDs, and reproducible samples. The full list with results is in the data report.

## Notes for the paper (limits)

- All methods see the time of the check-in they predict, as in the published setups (LLM-Mob, Nishida et al.).
  In real use the time of the next visit is not known in advance, so reported accuracy is an upper bound for that setting.

- The 500-instance NYC sample has a higher revisit rate (78.2%) than the full NYC test set (73.7%). This is ordinary
  sampling variation; report E2 rates on the sample alongside the full-set rate.
- Massive-STEPS Tokyo is small (334 test instances, median 10 check-ins per user) and has many short trajectories
  (median length 2), so E3 confidence intervals will be wide.
- Only 47% of Massive-STEPS test targets are revisits (vs about 74% for NYC/TKY), so its E1 numbers are not
  directly comparable with NYC/TKY.

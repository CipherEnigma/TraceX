# TraceX LLM pipeline, experiments and dashboard (Member 3)

This document covers how the LLM runs are produced, scored and shown. It builds on the data contract in
[data_pipeline.md](data_pipeline.md) and on Member 2's retrieval engine (`tracex_ir`), neither of which it modifies.
Results tables: [reports/llm/results.md](../reports/llm/results.md) (regenerated by `python -m tracex_llm.evaluate`).

## Reproduce

```bash
pip install -r requirements-llm.txt          # base requirements + transformers, bitsandbytes, streamlit
python -m tracex_data all                     # processed data (Member 1)

# LLM runs need a CUDA GPU; we use one Kaggle T4 for every run (notebooks/kaggle_run.ipynb)
python -m tracex_llm.run --dataset nyc --model qwen7b --sample sample_test_debug20   # always debug first
python -m tracex_llm.run --dataset nyc tky --model qwen7b                            # E1 + E2
python -m tracex_llm.run --dataset msteps_tokyo --model qwen7b --condition all       # E3
python -m tracex_llm.run --dataset msteps_tokyo --method retrieval --condition aliased --dry-run   # show a prompt, no GPU

python -m tracex_llm.evaluate                 # reports/llm/results.md + evaluation.json
python -m tracex_llm.report                   # reports/llm/figures/*.png|pdf
streamlit run app/dashboard.py                # dashboard
python -m pytest tests -q                     # 27 LLM tests run without a GPU or dataset
```

## Package layout (`tracex_llm/`)

| Module | Role |
|---|---|
| `config.py` | Every setting of an LLM run: models, 4-bit quantisation, decoding, prompt sizes, E3 conditions, file names |
| `prompts.py` | LLM-Mob and retrieval-demonstration prompt builders |
| `parse.py` | Answer parsing, invalid-ID and copy flags |
| `backends.py` | Hugging Face 4-bit backend (Qwen2.5) and a mock backend for tests |
| `run.py` | Resumable runner and CLI |
| `aliasing.py` | E3 venue-name aliases and the exported perturbed test sets |
| `stats.py` | Bootstrap CIs, paired bootstrap, McNemar, Holm (numpy only) |
| `evaluate.py` | E1/E2/E3 tables with paired statistics |
| `report.py` | Paper figures |

## Fixed settings (`tracex_llm/config.py`)

| Setting | Value | Why |
|---|---|---|
| Models | Qwen2.5-7B-Instruct, Qwen2.5-3B-Instruct | Brief: 7B plus a size comparison |
| Quantisation | 4-bit NF4, double quant, float16 compute | T4 has no bfloat16 |
| Decoding | greedy, `max_new_tokens=256`, `repetition_penalty=1.0` | Brief: temperature 0. Qwen's default penalty of 1.05 stays active under greedy decoding and pushes the model away from IDs in the prompt, which would bias the copy behaviour we measure, so it is reset to 1.0 |
| Batch size | 8, fixed for every reported run | Batched fp16 numerics can differ slightly from batch size 1 |
| Hardware | One Kaggle Tesla T4 for both models | Comparable accuracy and speed; the GPU name is stored with every run |
| Predictions requested | 10 ranked POI IDs | Needed for Acc@5 and NDCG@5 |
| LLM-Mob history | 40 most recent history check-ins, grouped by trajectory | LLM-Mob uses 40 historical stays |
| Retrieval | Jaccard, top 5 demonstrations, up to 20 context check-ins each | Brief names Jaccard/LCS selection; 5 is the low end of Nishida et al.'s 5-30 |
| Current trajectory | up to 30 most recent check-ins | Bounded prompt length |
| Target time in prompt | on (`INCLUDE_TARGET_TIME`) | LLM-Mob, LLM4POI and Nishida et al. all state when the next check-in happens |

## Prompts (`prompts.py`)

Every check-in is one line: `2013-01-02 12:39 Wednesday | POI 481 | Department Store` (plus `| "venue name"` on
Massive-STEPS when names are shown). The model must answer with
`{"prediction": [10 distinct integer POI IDs], "reason": "one short sentence"}`.

- **LLM-Mob:** `<history>` (recent trajectories, oldest first) + `<context>` (current trajectory) + the question.
- **Retrieval:** `<examples>` from Member 2's `retrieve_demonstrations` (query = the prefix only, candidates = the
  user's history), each ending `-> next: <check-in>`, + `<context>` + the question.

**Leakage rule.** The only target fields ever read are `time` and `weekday`, through `prompts.target_time()`. The
target's POI, category and name and the flags `target_in_history`, `target_in_prefix`, `is_revisit` are never read
when building a prompt. Checked on all 2,668 prompts of the three 500-samples (changing the target leaves every prompt
unchanged) and by `tests/test_llm.py`.

## Parsing and behaviour rates (`parse.py`)

Answers are read as JSON, then as a Python literal, then by regex on `"prediction": [...]`, then from "POI 123"
mentions. IDs are de-duplicated (first occurrence kept) and capped at 10.

- **Invalid IDs stay where the model put them.** They never match the target. Removing them would move later valid IDs
  up and inflate MRR/NDCG.
- **No padding.** Failed or short answers are not filled with heuristic guesses; a miss stays a miss.
- **Invalid rate** (brief): share of instances with no usable top-1 prediction (unparseable, empty, or a POI ID that
  does not exist).
- **Copy rate** (brief): share of all instances whose top-1 is a POI from the user's history or current trajectory
  (the same definition as `is_revisit`). `copied_top1_prompt` additionally records whether it was visible in the prompt.

Observed behaviour: Qwen-7B returned valid JSON for every NYC instance, and lists only POIs it can see. Retrieval
prompts often show only 2-5 distinct POIs, so many answers have fewer than 10 IDs; this caps Acc@5 for that method.
The frequency heuristic always pads its list with globally popular POIs, which a prompt cannot do. We report this as
a real difference between methods.

## Runs and result files (`run.py`)

One file per run: `results/llm/<dataset>/<dataset>__<model>__<method>__<condition>__<sample>.jsonl`, for example
`nyc__qwen7b__retrieval-jaccard__none__sample_test_500.jsonl`.

- **Resumable.** Each batch is appended and `fsync`ed; a re-run skips finished instances; a truncated last line from a
  crash or timeout is dropped and redone.
- **Settings guard.** `<run>.meta.json` holds a fingerprint of every setting (including the system prompt and, for E3,
  the alias version). Resuming with different settings is refused unless `--overwrite` is given, so a file never mixes
  two configurations. The meta file also records the GPU, library versions and timing of every session.
- **Record fields:** instance and run IDs, the raw answer, the parsed result with all flags, prompt metadata and a SHA-1
  of the prompt (the dashboard rebuilds the prompt and checks it matches), token counts and seconds. Scoring-only
  fields (`target`, `is_revisit`, `target_in_history`, `target_in_prefix`, `target_in_prompt`) are copied after the
  prompt is built.

## E3 name test (`aliasing.py`)

Massive-STEPS Tokyo is run three times on the same 334 instances: names **present**, **removed** (no name field), and
**aliased**. History, targets, POI IDs, categories and times are identical, so any accuracy change comes from names.

- One alias per `poi_id` (seed 42, generator `katakana-v1`), used everywhere the POI appears. Two branches of a chain
  get different aliases, so chain identity is removed as well (15% of Tokyo POIs share a name).
- Real names are 95% Japanese script (median 9 characters), so aliases are random katakana pseudo-words of similar
  length (median 7). "Aliased" then differs from "present" in meaning, not in script. Every alias is unique and never
  equals or occurs inside a real venue name.
- Checked: across 334 instances x 2 methods, the three prompts differ only in the venue-name spans, and no real name
  appears in a removed or aliased prompt.
- Release deliverable: `python -m tracex_llm.aliasing export` writes `data/perturbed/msteps_tokyo/` (three
  self-contained JSONL test sets with history embedded, `alias_map.csv` and a README).

The name test measures reliance on names, not proof that the data was memorised.

## Evaluation and statistics (`evaluate.py`, `stats.py`)

- **Metrics:** Accuracy@1, Accuracy@5, MRR and NDCG@5 against the target POI, plus copy and invalid rates. Rankings are
  cut to 10 for every method, so MRR is MRR@10 (Member 2 reports the heuristic's MRR over 20, slightly higher).
- **Heuristic floor:** Member 2's `frequency_baseline` is recomputed on exactly the same instances, so every comparison
  is paired.
- **Uncertainty:** 95% percentile bootstrap CIs (10,000 resamples, seed 42); differences by paired bootstrap; McNemar
  on Acc@1 and Acc@5 (exact binomial below 25 discordant pairs, chi-square with continuity correction otherwise);
  Holm-Bonferroni correction within each table (E1, E2, E3, model size).
- **E1** uses the realistic setting of each dataset (no names; names present on Massive-STEPS). **E2** splits every E1
  comparison into revisit and new targets. **E3** compares the three name conditions per model and method. **Model
  size** compares 7B and 3B for each matching setting. Partial runs are marked and compared on their finished
  instances only.

## Kaggle (`notebooks/kaggle_run.ipynb`)

`STAGE = "all"` runs everything in one *Save Version -> Save & Run All*: for each model in turn (7B, then 3B, on the
same T4) a 20-instance debug run, a sanity check (more than 20% invalid answers skips that model), E1 and E3, then
`tracex_llm.evaluate` and `tracex_llm.report`. A failed run is logged and the rest continue. Single stages (`debug`,
`gate1`, `e1`, `e3` with one `MODEL`) still work. The notebook pins one T4, clones the branch, rebuilds the data and checks the evaluation samples match the committed
ones, restores earlier results from an attached dataset (so finished runs are skipped), runs the stage, writes
`tracex_llm_results.zip` after every run, and prints measured speed and the Gate 1 check. A private repo can be cloned
with a `GITHUB_TOKEN` Kaggle secret; the token never appears in output.

Measured on a Tesla T4: Qwen2.5-7B takes 3.6-4.2 s per instance (prompts of about 800-1,700 tokens, answers of about
80 tokens), so the full plan is about 4.2 GPU-hours per model.

## Dashboard (`app/`)

`streamlit run app/dashboard.py`. Six pages built from the Claude Design boards: Overview, E1 Heuristic floor, E2
Revisit vs new, E3 Name test, Instance explorer, Runs & behaviour, plus page 7, Personal assistant (below). It reads `results/llm/` live (new Kaggle results
appear on refresh) and uses `tracex_llm.evaluate`, so every number matches `reports/llm/results.md`. Theme tokens are
in `.streamlit/config.toml` and `app/tracex.css`; light and dark are both defined (switch in the ⋮ menu at the top right).
`TRACEX_RESULTS_DIR=<folder>` points it at another results folder.

## Personal assistant: the grounded LLM layer (`tracex_assist/llm.py`)

Our experiments show the LLM copies habits rather than reasoning, so in the assistant **IR decides and the LLM only
explains**. Member 1's profile and Member 2's evidence engine produce an `Evidence` object (contract:
`tracex_assist/contract.py`, plan: [assistant_plan.md](assistant_plan.md)); this layer turns it into an answer.

| Step | What it does |
|---|---|
| Intent | `parse_intent(question)` → `want_new` ("somewhere new", "haven't tried") and `want_kind` (food, coffee, drinks, shopping, outdoors, transport), set in the `Context` **before** evidence is gathered |
| View | `evidence_view(ev, places)`: readable place labels ("Coffee Shop #345", or the real Tokyo name) and every number pre-written as text ("you went there next 11 of 20 times (55%)"). New places are included only when asked for. This view is the only thing the model sees |
| Prompt | 11 rules: use only the evidence, copy numbers exactly, never call a known place new, no facts or opinions not in the evidence, at most 120 words |
| Model | `qwen2.5:3b` through a local [Ollama](https://ollama.com) server (`/api/chat`, temperature 0.2), standard library only; nothing leaves the laptop |
| Validator | Every `#id`, percentage, "N of M" count and distance in the answer must occur in the view, and a distance must sit in the same sentence as the place it belongs to (by `#id` or name) |
| Retry / fallback | One retry with the problems listed, then `fallback_answer()`: a template built from the same evidence (also used when Ollama is not running), itself checked by the validator in the tests |

Measured on 50 varied questions (2 datasets × 5 users × 5 question types, RTX 4050 laptop): 94% of answers accepted
first time, 98% after one retry, 2% template; 1-2 s per answer once the model is loaded. Every rejection was a real
error (invented percentage or count, misplaced distance). Tests: `tests/test_assist_llm.py` (24, no Ollama needed).

## Limits to state in the paper

- The prompt tells the model when the next check-in happens (as in the published setups). The target's place is never
  shown.
- Retrieval prompts can show fewer than 10 distinct POIs, which caps Acc@5 for that method (see Parsing above).
- 4-bit quantisation and batched fp16 decoding can differ slightly from full-precision, batch-1 results.
- Massive-STEPS Tokyo has 334 test instances and only 47% revisit targets, so E3 intervals are wide and its E1 numbers
  are not directly comparable with NYC/TKY.
